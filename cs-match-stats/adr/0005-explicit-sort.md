# ADR-0005. Явный параметр сортировки в GET /matches

- **Статус:** принято
- **Дата:** 2026-09-24
- **Закрывает:** [Q-2](../README.md#вопросы-к-контракту)
- **Дополняет:** [ADR-0002](0002-offset-pagination.md)

## Контекст

В v1.0 порядок матчей в `GET /matches` не был зафиксирован. С offset-пагинацией ([ADR-0002](0002-offset-pagination.md)) это опасно: если база вернёт записи в другом порядке, страницы будут дублировать или терять матчи.

Клиентам нужны два порядка:

- **расписание:** ближайшие матчи первыми, по `startsAt` от ранних к поздним;
- **результаты:** свежие матчи первыми, по `startsAt` от поздних к ранним.

## Решение

- В `GET /matches` добавлен параметр `sort` со значениями `startsAt` и `-startsAt`. По умолчанию `-startsAt`.
- При одинаковом `startsAt` матчи всегда дополнительно сортируются по `id` — это делает порядок полностью детерминированным.
- Неизвестное значение `sort` → `400` с кодом `INVALID_PARAMETER`, как и для других параметров.
- В `GET /events` порядок фиксированный и описан в контракте: по `startDate` от новых к старым, затем по `id`.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Направление зависит от фильтра: `upcoming` по возрастанию, `finished` по убыванию | «Магия»: поведение неочевидно из запроса, и непонятно, что делать без фильтра по статусу |
| Сортировка по любому полю (`sort=eventName`, `sort=format`…) | Нет таких сценариев в историях, а каждое поле сортировки — отдельный индекс в базе |
| Оставить порядок неопределённым | Ломает offset-пагинацию, см. контекст |

## Последствия

- ➕ Порядок виден прямо в запросе, страницы стабильны.
- ➕ Изменение обратно совместимо: параметр необязательный, а раньше порядок вообще не гарантировался.
- ➖ Клиенты, которым нужно расписание, должны явно передать `sort=startsAt`.
