# ADR-0002. Пагинация через limit/offset с полем total

- **Статус:** принято
- **Дата:** 2026-09-24. Решение записано задним числом: оно уже отражено в `openapi.yaml` v1.0.0.

## Контекст

`GET /matches` возвращает от десятков до сотен матчей: расписание, live, матчи турнира. Клиентам нужно:

- показывать страницы и общее число матчей («137 матчей»);
- переходить на произвольную страницу;
- обходиться без сложной логики на своей стороне.

## Решение

- Параметры запроса: `limit` (1–100, по умолчанию 20) и `offset` (от 0, по умолчанию 0).
- Ответ: `{ items, total }`, где `total` — сколько всего записей подходит под фильтр.
- Значения вне диапазона → `400` с кодом `INVALID_PARAMETER`.
- Смещение за пределами выборки → `200` с пустым `items` и честным `total`.

## Рассмотренные альтернативы

| Вариант | Плюсы | Почему не выбран |
|---|---|---|
| Курсорная пагинация | Страницы не «плывут» при вставках, глубокие страницы не дорожают | Нельзя перейти на страницу N, `total` не получить дёшево, клиентам сложнее |
| `page` / `size` | Привычно для UI | То же, что offset, только менее гибко |

## Последствия

- ➕ Просто для клиентов, `total` сразу есть для интерфейса.
- ➖ Если между запросами появились новые матчи, записи на страницах сдвигаются: возможны дубли и пропуски. Нужен детерминированный порядок сортировки, а в контракте его пока нет — см. [Q-2](../README.md#открытые-вопросы).
- ➖ Большие `offset` дороже для базы. При текущих объёмах это приемлемо. Если понадобится выгрузка полной истории матчей (тысячи записей), вернуться к курсорной пагинации.
