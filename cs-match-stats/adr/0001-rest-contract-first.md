# ADR-0001. REST API с контрактом OpenAPI (contract-first)

- **Статус:** принято
- **Дата:** 2026-09-24. Решение записано задним числом: оно уже отражено в `openapi.yaml` v1.0.0.

## Контекст

API потребляют внешние приложения разных команд на разных стеках. Данные только читаются, ресурсов два: список матчей и матч. Нужно:

- согласовать контракт с потребителями до начала разработки;
- генерировать из контракта клиентов, моки и документацию;
- кэшировать ответы стандартными средствами HTTP.

## Решение

- REST поверх HTTPS, формат JSON.
- Контракт описан в OpenAPI 3.0 ([openapi.yaml](../openapi.yaml)) и считается единственным источником правды. Сначала меняется спецификация (через pull request с ревью и линтером), потом код.
- Версия API — в URL (`/v1`). Внутри v1 допустимы только обратно совместимые изменения, ломающие изменения уходят в `/v2`.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| GraphQL | Гибкие выборки не нужны для двух read-only ресурсов. HTTP-кэширование сложнее, и нужно отдельно защищаться от тяжёлых запросов |
| Code-first: спецификация генерируется из кода | Контракт появляется только после реализации, согласовать его с потребителями заранее нельзя |

## Последствия

- ➕ Клиенты и моки генерируются из спецификации, документация (Swagger UI) публикуется автоматически.
- ➕ Линтер Spectral в CI ловит ошибки контракта ещё на ревью.
- ➖ Спецификацию нужно поддерживать вручную и следить, чтобы код ей соответствовал. Следующий шаг — контрактные тесты по критериям из [user-stories.md](../user-stories.md).
