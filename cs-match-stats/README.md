# CS Match Stats API — кейс системного аналитика

Публичный API статистики матчей Counter-Strike 2. Кейс проходит всю цепочку работы аналитика: проблема → требования → архитектура → данные → контракт → поведение → решения.

Формат docs-as-code: всё лежит в репозитории в Markdown и mermaid, изменения проходят через pull request, контракт проверяется в CI.

**Документация API:** [Swagger UI](https://ifuzys.github.io/git-practice/), исходник — [openapi.yaml](openapi.yaml).

## Проблема

Статистика профессиональных матчей CS2 разбросана по сайтам турниров, трансляциям и агрегаторам. Форматы у всех разные, идентификаторы команд не совпадают. Разработчики фан-приложений, медиа и аналитических сервисов парсят HTML и сводят данные вручную. Это дорого и медленно, а сбор ломается при любом изменении вёрстки источника.

**Цель:** единый стабильный API с расписанием, live-счётом и результатами по картам в одном формате.

**Метрики успеха:**

- новый клиент интегрируется за один рабочий день;
- live-счёт в API отстаёт от события не больше чем на 10 секунд.

## Стейкхолдеры

| Стейкхолдер | Интерес | Взаимодействие |
|---|---|---|
| Разработчики клиентских приложений (фан-приложения, медиа) | Стабильный контракт, понятные ошибки, предсказуемая пагинация | Потребляют API |
| Аналитики, в том числе беттинг-аналитики | Полные и корректные результаты по картам, рейтинг на момент матча | Выгружают историю матчей |

| Product owner | Покрытие турниров, скорость обновления live | Приоритизирует бэклог |
| Команда разработки и поддержки | Однозначные требования, наблюдаемость | Реализует и сопровождает |

## Скоуп v1

**В скоупе:**

- список матчей с фильтрами по статусу и турниру, с пагинацией;
- детали матча: команды, формат серии, счёт по картам;
- рейтинг команд на момент матча;
- единый формат ошибок.

**Вне скоупа:**

- статистика игроков (K/D, ADR, рейтинг игрока);
- коэффициенты букмекеров;
- авторизация и тарифы: v1 — публичный API только для чтения;
- админка для ручной правки данных;
- push-уведомления клиентам (вебхуки, стриминг): в v1 клиенты опрашивают API сами.

## Глоссарий

| Термин | Значение | В API |
|---|---|---|
| Матч (серия) | Противостояние двух команд в формате bo1, bo3 или bo5 | `Match` |
| Формат | Сколько карт нужно выиграть: 1 из 1, 2 из 3, 3 из 5 | `Match.format` |
| Карта | Одна игра внутри серии. Играется до 13 выигранных раундов, при 12:12 — овертаймы | `MapResult` |
| Вето | Процедура банов и пиков карт перед матчем | — |
| Пик | Карта, которую команда выбрала на вето | `MapResult.pickedBy` |
| Десайдер | Последняя карта серии, оставшаяся после вето; её никто не пикал | `pickedBy` не передаётся |
| Турнир | Соревнование, в рамках которого играются матчи | `eventId`, `Match.eventName` |
| Мировой рейтинг | Место команды в мировом рейтинге на момент матча | `Team.worldRanking` |
| Статус матча | `upcoming` → `live` → `finished`, см. [match-lifecycle.md](match-lifecycle.md) | `MatchStatus` |

## Нефункциональные требования

Целевые значения для v1.

| Характеристика | Требование |
|---|---|
| Производительность | 95-й перцентиль времени ответа: до 300 мс для `GET /matches/{matchId}`, до 500 мс для `GET /matches` при `limit` ≤ 100 |
| Свежесть данных | Счёт live-матча в API обновляется не позже чем через 10 секунд после события у провайдера |
| Доступность | 99,5 % в месяц |
| Совместимость | Внутри v1 только обратно совместимые изменения ([ADR-0001](adr/0001-rest-contract-first.md)) |
| Качество контракта | `openapi.yaml` проходит Spectral без ошибок и предупреждений, проверка в CI |

## Открытые вопросы

Нашлись при разборе контракта и историй. Каждый — кандидат в бэклог v1.1.

| # | Проблема | Чем грозит | Предложение |
|---|---|---|---|
| Q-1 | Фильтр `eventId` есть, но в `Match` нет поля `eventId`, а справочника турниров нет | Клиенту неоткуда узнать ID турнира: фильтр работает только по договорённости | Добавить `eventId` в `Match` (обратно совместимо) и эндпоинт `GET /events` |
| Q-2 | В контракте не зафиксирован порядок сортировки `GET /matches` | При offset-пагинации страницы могут дублировать или терять матчи | Сортировать по `startsAt` (для `finished` — от новых к старым), при равенстве — по `id`. Описать это в контракте |
| Q-3 | В `MapResult` нет признака, что карта завершена | В live-матче не отличить сыгранную карту от текущей | Добавить в `MapResult` поле `status` со значениями `live` и `finished` |
| Q-4 | Нет статуса для отменённых матчей и технических поражений | Непонятно, как отдавать такие матчи. Новое значение в `MatchStatus` сломает клиентов, которые строго проверяют enum | Принять решение отдельным ADR: новый статус в v2 или уже сейчас требовать от клиентов игнорировать незнакомые значения |

## Проверки в CI

- **OpenAPI lint** ([workflow](../.github/workflows/openapi-lint.yml)). На каждый pull request [Spectral](https://github.com/stoplightio/spectral) проверяет спецификацию по правилам [.spectral.yaml](../.spectral.yaml): стандартный набор `spectral:oas` и собственные правила стиля (camelCase для `operationId`, kebab-case для путей). Сборку роняют и ошибки, и предупреждения.
- **API docs** ([workflow](../.github/workflows/api-docs.yml)). После merge в `main` Swagger UI со свежей спецификацией публикуется на GitHub Pages.
